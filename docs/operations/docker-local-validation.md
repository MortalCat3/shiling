# Docker 本机部署与恢复验收

- 日期：2026-11-17。
- 环境：macOS ARM64 上的 Docker Desktop 29.8.2 / Compose 5.5.1；实际容器为 Linux ARM64。
- 组件：Node 24.22.3、pnpm 12.21.0、PostgreSQL 18.7（bookworm）、Caddy 2.11.9、FFmpeg 5.1.9（Debian 包）。
- 边界：随机命名的两组 Compose 项目、独立网络及命名卷，仅回环 HTTP；未连接宿主数据库、历史平台、其他容器实例或外部对象存储。全部账号、图片和 MP4 均为合成验收数据。

本机 Docker 启动、真实业务、数据持久化、重启和较早备份恢复已经通过。此结论不等于生产 HTTPS、容量、异地恢复和目标服务器环境已验收。

## 本次修复

1. **数据库初始化与假就绪**：实际首次启动时，宿主挂载脚本无法执行，PostgreSQL 随后重启并跳过初始化；单纯 `pg_isready` 却仍可能成功。现在使用独立 `postgres` 镜像目标，固定引导脚本/SQL 的权限及父目录遍历权限。健康检查使用受限 app 角色通过 TCP 验证专用库、扩展和最小授权；空卷复测成功，未完整引导时保持失败。
2. **worker 临时目录**：默认相对临时目录会落入只读根文件系统；Compose 明确配置 `/tmp/shiling-media`，真实图片和 MP4 处理已验证。
3. **构建上下文**：排除 `.impeccable` 本地评审缓存、截图和目录；环境文件与 Git 历史继续不进入镜像。
4. **恢复操作顺序**：手册原先将“所有者重新发布”写在公开入口开启之前，与 API 的发布前置条件不符。现明确为先核对、显式开启入口（withdrawn 不复活），再由各所有者重新发布。
5. 补充可指定新输出目录且拒绝覆盖的随机 secret 生成方式、交付签名 secret 示例和可重复 Docker 验收脚本。验收脚本中不兼容当前 Compose 的 `create --no-deps` 已修正，恢复成功结果来自修正后的复测。

## 已通过的实际检查

| 范围           | 实际验证                                                                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 镜像与启动     | runtime、web、postgres 三类镜像构建；全新卷引导；owner/migrate/app 三角色；正式迁移连续运行两次；五个常驻服务启动                                            |
| 容器权限       | API/worker/preview 为 node 用户、只读根文件系统、撤销 Linux capabilities、禁止提权；数据库与应用无宿主端口；preview 无 secret/对象挂载                       |
| 数据库权限     | 业务和队列表归 `shiling_owner`；`shiling_app` 非超级用户，无建库/建角色/schema CREATE/owner 成员权限；真实 DML 与队列处理成功                                |
| 真实业务       | Caddy 正式同源入口通过工作台 12 组 HTTP 用例：初始化、会话、邀请、角色、成员、品牌 PNG/JPEG/WebP、图片/MP4、集合、公开快照、下载/Range、密码恢复、任务与审计 |
| 入口隔离       | `/objects/`、`/uploads/`、`/preview/`、`/internal/` 探测均 404；正式前端路由返回构建产物；动效能力关闭且上传返回 403                                         |
| 持久化         | 重启数据库及所有应用，再移除容器/网络并保留命名卷重建；账号、设置、公开状态、集合和素材仍在；图片/视频六个产物及 Logo/favicon 的 SHA-256 一致                |
| 单独数据库重启 | 不手动重启应用，仅重启 PostgreSQL；API 由容器重启策略恢复一次，worker 保持运行；重新登录、公开读取、品牌读取和新上传处理通过；没有 OOM                       |
| 一致备份       | 停 web/API/worker/preview，确认目标库无其他客户端；取 `pg_dump -Fc` 和对象卷归档；检查 dump 目录、tar 可读性与 SHA-256；保留源卷                             |
| 全新卷恢复     | 恢复目标独立于源实例；数据库及对象还原后、任何业务启动前执行灾备 dry-run/apply/verify；`safe=true` 后才启服务                                                |
| 数据回退       | 备份后在源实例修改标题；恢复副本保持备份时标题，证明恢复的是备份点；原件、派生图片/视频、品牌与集合保持一致                                                  |
| 旧资格失效     | 旧管理员/成员 cookie 返回 401，旧邀请和恢复令牌返回 410；尚未过期的旧 grant 返回 404；待核验上传变为 `RESTORE_EPOCH_REVOKED`，新 worker 不续跑旧上传         |
| 恢复后运行     | 新会话可正常使用；新上传可 ready；轮换 CSRF/交付/初始化密钥并重建应用后可再次认证                                                                            |
| 重新公开       | public off、active 全部撤回；显式重开入口不会复活 withdrawn 快照；管理员代发布 403，所有者重新发布成功，游客下载摘要正确                                     |

灾备动作实际撤销 7 个未撤销会话、2 个未消费一次性令牌、1 个 active 公开记录、1 个活动上传尝试与上传项；动作后计数均为 0，运行 UUID 轮换，公开/预览访问代次递增。旧 grant 检查时仍未到期，检查期间先保留相同签名密钥，之后再轮换，避免仅靠签名变化或自然过期掩盖数据库安全处理。

本次小型合成备份约 212 KB（数据库）与 10 KB（压缩对象）。成功复测从开始还原到服务就绪为 **23.263 秒**，不含镜像拉取、备份、此前排错、人工检查、资格验证和重新公开。这不是生产 RTO；本次数据缺口仅为刻意写入的备份后标题标记，也不是生产 RPO 承诺。

## 复现与收尾

执行入口、凭据边界和完整命令见[Docker 验收脚本说明](../../tests/deployment/README.md)。脚本复用[工作台 HTTP 套件](../../tests/e2e/workbench-regression.mjs)，增加重启、停写备份、新卷还原和恢复业务断言。

本轮工程检查通过：最终三类镜像构建（包含全工作区构建）、项目边界检查、全仓 ESLint、改动文件格式检查和 shell 语法检查。使用最终镜像重建恢复实例后，再次通过登录、品牌/公开读取与新上传处理。未重复执行会重建宿主测试库的集成套件，也未重复桌面/手机视觉测试；本轮未修改前端或业务权限代码。

验收实例停止后保留本次专用卷与系统临时目录中的私有备份，以供本机复核；失败的空初始化实例也停止，未删除其他实例、镜像或卷。没有发布镜像、外网部署或修改默认 Docker context。临时目录中的凭据和备份不能提交，也不是长期灾备保管位置。

本轮没有修改界面设计或权限规则。实际生产仍需完成域名/DNS/HTTPS 与 Secure cookie、目标服务器/CPU 架构、代表性真实媒体与负载、长期容量/告警、异地加密备份可取回、升级回滚和目标 RPO/RTO。S3 未提供正式适配器；HTML/ZIP 动效上传和执行继续保持关闭。
