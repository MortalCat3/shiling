## 2. 授权模型与不可配置的安全边界

一次授权同时满足以下条件：

1. **请求主体**：请求主体类型正确；用户存在、有效、会话未撤销；服务主体使用独立可信凭据。
2. **权限**：当前角色拥有该用例的固定能力；未知能力默认拒绝。
3. **所有权／范围**：满足本人资源或明确的跨所有者治理能力；公共能力只对应特定公开版本。
4. **资源状态**：资源处于允许执行该动作的状态，版本、revision 和任务栅栏有效。
5. **实例策略**：公开、上传、动效执行等开关允许该动作，且未超过已配置限额。

前端 capability 只用于显示入口与说明；后端 HTTP、文件交付、任务完成提交、公开检索均独立执行授权。角色编辑器不能关闭这些检查。

以下约束在任何角色中都不能越过：

- 没有 `publishAny`；公开、再次公开、更新公开快照必须由素材所有者执行。
- 收藏只属于当前用户；没有查看或修改他人收藏的产品能力，系统管理员也不例外。
- 集合成员关系、相同文件哈希、知道素材 ID、持有旧链接均不产生素材编辑或公开权限。
- 不接受客户端传入的 ownerId、userId、roleName、storageKey 作为授权依据；所有权和角色从服务端记录解析。
- 账号禁用、会话撤销、公开撤回、资源归档的结果不能被陈旧缓存或迟到任务覆盖。
- 未通过处理校验的文件不能进入团队可用目录或公开；文件名、扩展名、浏览器 MIME/hash 不替代服务端验证。
- 首期没有永久删除、账号删除、转移素材所有者、隐式公开整集合、任意脚本权限条件。

补充规则：

- 按已确认 D02，默认 member 不拥有 `tags.manage`；上传不强制先创建标签。给本人素材选择已有标签依赖 `assets.editOwn`，不另增标签关系权限。
- `assets.governAny`、`uploads.governAny`、`collections.governAny`、`publications.withdrawAny` 可由系统管理员授予可信自定义角色，用于表达整理员；初始 member 没有这些能力。
- 只有 `system.*` 保留给不可编辑的系统管理员角色，不能委派给自定义角色。系统管理员具有目录内全部能力，但所有权等不可配置限制仍然生效。
- 撤回是降低公开范围的动作，`withdrawOwn` 与 `publishOwn` 分开；移除某角色 publishOwn 后，可保留其撤回本人公开的能力。
- 能力依赖在角色保存时校验：例如 `assets.download` 依赖 `assets.read`，`assets.editOwn` 依赖 `assets.read` 和 `tags.read`，创建/维护集合依赖 `collections.read` 与 `assets.read`。不得悄悄补上不显示的权限；界面展示依赖并显式保存完整集合。
- 自定义角色的展示名称不能使其获得系统管理员身份；服务端依据固定角色标识和系统属性判定，不依据名称字符串。

## 4. 角色、会话与账号生命周期

### 4.1 单角色与角色配置

首期一个用户只有一个 `roleId`，不引入多角色合并、负权限或逐资源 ACL。系统管理员角色为系统记录，不可改名、改权限、归档或删除。内置 member 是默认普通能力模板；其他实例可创建只读、上传者、整理员等自定义组合。

只有当前有效系统管理员能管理角色和给用户分配角色。邀请时选择普通角色属于 `system.members.manage`；已有成员的角色变更属于 `system.roles.manage`，包括后续提升为系统管理员。自定义角色提交未知 key 或任何 `system.*` 必须失败，不能自动过滤后保存。业务治理能力在编辑器中标明“影响他人或整个团队”，但不把正常保存变成额外运维审批。

角色有 revision。归档仍被账号或有效邀请引用的角色应返回冲突，要求先显式重新分配或撤销邀请；不静默把用户降为默认 member。账号、角色和邀请不通过物理删除来绕过审计。

### 4.2 禁用、撤销与实时授权

禁用用户在一个事务内更新账号状态、递增授权代际并撤销其全部会话。角色分配变化或角色能力变更递增相应授权 revision。每个受保护请求必须依据服务端当前状态判定；首期不以有过期窗口的本地 permission 缓存作为最终依据，也不信任长效 JWT 内的旧角色声明。

“立即生效”定义为：禁用/撤销事务提交后，新的受保护请求、新下载签发和新的写入提交均被拒绝。已下载字节、已签发对象 URL、已建立的外部传输不在即时回收保证内，按第 7 节限制窗口。页面收到身份失效后停止轮询、清空私有展示缓存并返回登录态，但 UI 清理不能代替服务端拒绝。

已经通过入口检查的长任务在提交副作用前必须重新校验：账号是否有效、当前角色是否仍有发起能力、任务 revision/取消栅栏、资源当前状态及策略。身份检查与关键 DB 提交必须有明确串行化点；不能在网络 I/O、转码或录制期间持有长事务。

### 4.3 最后管理员与账号恢复

停用、降权或其他会导致当前实例没有有效系统管理员的操作必须在事务内拒绝；并发处理两个管理员时，也不能各自看到另一个仍有效而一起成功。自我降权/停用只在存在另一个有效系统管理员时允许，并明确会结束本人的相关会话。

首期不删除账号。账号恢复/密码重置通过受控管理员操作或本机可信管理命令完成，使用一次性、短效、不可记录明文的恢复凭据；重置后撤销旧会话。恢复已禁用账号不会复活旧会话，用户需重新登录。

账号停用不自动归档其已入库素材、不自动撤回历史公开。管理员可另行治理或撤回；账号治理和内容治理分别审计。所有者未恢复时，管理员仍不能替其公开或更新公开快照。

### 4.4 会话与浏览器请求边界

会话 cookie 使用主站 host-only、Secure、HttpOnly 属性与明确 SameSite 策略，生产不设共享父域 Domain；优先使用满足约束的 `__Host-` cookie。预览域不能读取或复用主站 cookie。所有改变状态的浏览器请求校验精确允许的 Origin，并使用与会话绑定的 CSRF 防护；CORS 不开放携带凭据的通配来源。`GET` 不执行公开、撤回、归档、邀请或角色变更等副作用。

登录、激活、恢复和邀请具有独立的滥用防护与限额，不通过登录错误区分账号是否存在。授权令牌和恢复凭据均不进入浏览器持久业务存储、公开链接或访问日志。具体会话有效期、登录限额和恢复凭据 TTL 在部署参数中冻结，不在本文虚构数字。

## 5. 请求主体 × 权限 × 所有权 × 状态 × 实例策略

`ready` 指版本处理已合格并可进入团队目录；“未归档”是独立维度。以下是授权语义，不要求 HTTP DTO 把多个状态混为单字段。

与领域模型的命名对齐：`Asset.lifecycle = pending | active | archived`，`AssetVersion.processingState = processing | ready | failed | canceled`；正常团队读取要求 active 且 currentVersionId 指向 ready 版本。`UploadItem.transportState = pending | uploading | verifying | verified | failed | canceled | expired` 只描述接收阶段。verified 后取消作用于尚未 ready 的处理版本，不把 transportState 倒退为未上传；ready 后取消仍为 409。Publication 独立采用 active / withdrawn。所有表中的“ready 素材”均为上述组合条件的简称。

| 公开目录/详情/下载     | 匿名，或按公开视图访问的用户                                                    | Publication active、绑定版本 ready、素材未归档                                                                           | 公开开关开启；只查公开投影并核对当前资格                                                                                                                                      |
| 标签字典维护           | 有效用户＋`tags.manage`                                                         | 全局标签记录；revision 匹配                                                                                              | 可影响内部关联和检索；不因此改写任何公开快照                                                                                                                                  |
| 集合读取               | 有效用户＋`collections.read`＋`assets.read`                                     | 团队集合未归档；只返回当前可读条目                                                                                       | 不对游客暴露内部集合、集合统计或名称                                                                                                                                          |
| 集合创建/条目治理      | `collections.create`；owner＋`collections.manageOwn` 或 `collections.governAny` | 可加入任意有权读取的 ready、未归档素材，包括他人的素材                                                                   | 集合权限不提供修改素材标签/标题/公开的权限                                                                                                                                    |
| 集合归档/恢复          | owner＋`collections.manageOwn` 或 `collections.governAny`                       | 集合 revision 匹配                                                                                                       | 不归档素材、不改变公开，不自动公开整个集合                                                                                                                                    |
| 收藏                   | 有效用户＋`favorites.manageOwn`                                                 | userId 永远取当前用户；增加时目标可读                                                                                    | 素材归档后隐藏不可读条目，允许本人移除；恢复后可重新显示保留关联                                                                                                              |
| 系统管理               | 系统管理员＋对应 `system.*`                                                     | 需 revision；成员/角色变更保护最后管理员                                                                                 | 系统设置不接收云凭据、任意代码或上传的执行插件                                                                                                                                |

### 5.1 标签与集合的特殊边界

- `tags.manage` 是显式的全局治理能力：首期仅创建、改名、停用和恢复，维护唯一约束、引用完整性与审计；标签合并移至后续，不提供首期入口。这不等于取得素材公开权。
- 停用标签保留历史关联以便追溯，禁止新增关联；恢复后可再次选择。首期不永久删除标签。公开快照里已确认的标签文字不随字典变化。
- 普通成员能给本人素材选择有效标签，不能仅凭“自己在素材上用过这个标签”改名或停用该标签。
- 集合创建者与具备 `collections.governAny` 的治理者可增删条目；素材作者并不因此自动成为他人集合的维护者。作者仍能修改或归档自己的素材，集合展示必须过滤已归档/不可读素材。
- 集合归档/恢复属于 `collections.manageOwn` / `collections.governAny`，只改变集合的生命周期；不批量归档、恢复或公开其中素材。
- 批量资产操作（例如标签与归档）按 Asset 逐项授权并返回成功、拒绝、冲突等结果，不因第一项获准而放行整批。一个集合的条目批量操作则在同一个集合事务中原子执行：检查集合权限/revision 及所有目标素材资格，任一失败整批不变；不能把这两类批量接口统一成部分成功语义。
- 重复文件检测仅给出不阻塞的提示。用户可继续创建独立 Asset、Version 和产物引用；首期不做全局物理去重，也不让两个素材因哈希相同共享所有权、公开状态或归档行为。

## 6. 工作进程、令牌和执行器不是用户角色

| 主体                | 可以做什么                                                                                            | 不能做什么                                                           |
| ------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 普通用户会话        | 当前角色和所有权允许的业务用例                                                                        | 伪造 worker 结果、直接选择存储 key、绕过 revision                    |
| 队列 worker         | 领取已授权任务、读取指定输入、请求受限执行、校验 manifest 并提交结果                                  | 以管理员身份调用任意 API；把处理成功当作公开授权                     |
| 动效/媒体执行器     | 读取单任务输入、在限制内生成产物、返回待验证 manifest                                                 | 持有主站 cookie、数据库连接、长期对象存储凭据；访问任意公网/宿主文件 |
| 内部预览 capability | 有限 TTL 内绑定指定版本/产物和主站 session 的服务端引用；预览服务据引用复核 session、用户与资源仍有效 | 作为用户身份、角色或其他素材访问凭据；要求 iframe 携带主站 cookie    |
| 公开预览 capability | 绑定特定 Publication revision、版本、动作和实例公开 epoch                                             | 绕过撤回、归档或公开关停；变为团队读取凭据                           |
| 对象存储签名 URL    | 在供应商支持的范围和 TTL 内访问单对象/指定方法                                                        | 代表 member/admin；执行公开、编辑、枚举或读取其他对象                |

任务必须携带业务目标、处理步骤、输入版本、processorVersion、attempt/lease 与取消栅栏。提交结果时由可信服务重新加载当前任务与资源，检查执行归属、状态、输入/输出 manifest 和对象摘要，不信任执行器自报 owner 或 ready。

素材 owner 被禁用或失去 `uploads.create` 后，已接受但尚未 ready 的版本不能因为 worker 持有技术凭据而入库。提交时将 `AssetVersion.processingState` 记为 `failed`，安全错误码为 `AUTHORIZATION_REVOKED`，保留可诊断证据，不作为普通技术失败自动重试。恢复 owner 账号与上传权限后，仍需本人或有权治理者明确手动 retry 并重新授权；不会因恢复账号或权限自动复活任务。owner 仍 disabled 或仍无 `uploads.create` 时，管理员持有 `uploads.governAny` 也不能绕过该约束。已经 ready 的素材后续生成可选封面等派生物，以素材当前状态和任务目的授权，不机械要求历史上传者仍有上传权。

动效包首期只执行自包含静态 HTML/ZIP。预览域不共享主站身份 cookie；包内脚本不得访问主站、外网、云元数据、宿主 Secret、任意文件系统或其他任务。iframe sandbox、CSP 与执行器网络/资源限制不可由上传包声明覆盖。部署不能提供隔离条件时，明确禁用执行预览；安全封面和获准的源包下载可继续存在。

内部 motion grant 绑定的是服务端可解析的主站 session 引用，不暴露 session cookie 值；主站先经会话鉴权签发 grant，iframe 只提交受限 grant。预览服务端通过可信内部查询复核该 session 未撤销、用户/角色仍有效及资源可读，不能要求跨 origin 的 iframe 发送主站 cookie。`executePreview=false` 阻止新交互及需要执行动效包的处理步骤；已有 ready 静态封面可继续按权限读取。

## 7. 公开快照、撤回与缓存合同

### 7.1 公开投影

Publication 记录绑定具体 ready 版本、公开元数据快照和独立 revision。公开目录、详情、标签筛选、搜索摘要、Open Graph/分享元数据以及下载文件名都从公开白名单构建，不能序列化内部 Asset DTO 后只删几个字段。

推荐公开字段：公开 ID、公开标题、公开说明、已确认公开标签文字、类型、必要的尺寸/时长/格式/大小、公开时间，以及经授权产生的预览/下载入口。公开下载名称由公开标题和可信格式生成。

发布或更新公开快照的 `publicMetadata` 输入只接受 `title`、`description`、`tagIds`。`tagIds` 必须是该 Asset 当前已关联标签的子集，不能借公开操作添加内部标签关系；服务端读取标签 label 并固化为快照，不信任客户端传入的 label。公开 DTO 返回 `publicTags` 字符串数组，不含团队 tagId；公开标签查询使用快照中的标签文字，不能复用内部标签 ID 查询或内部字典。

禁止公开字段：成员姓名/头像/ID、账号、邀请、内部 owner/creator、内部集合、原始上传路径、未经确认的原始文件名、内部备注、处理失败明细、上传批次/任务/审计标识、bucket/key、数据库 ID 映射、Secret。用户手工写入公开说明或文件内容的个人信息不能靠字段白名单自动清除，公开确认页应显示即将公开的实际内容。

公开素材正文里的“作者/来源/许可”若以后作为独立内容字段引入，必须与成员身份分离并另行确定范围；本稿不把成员资料当作作者信息自动输出。

### 7.2 新请求与既有授权的不同保证

| 事件              | 提交后的新请求                                                 | 提交前已发出的授权                                                    |
| ----------------- | -------------------------------------------------------------- | --------------------------------------------------------------------- |
| 撤回公开          | 不再返回该公开详情、不再签发公开文件/预览资格                  | 应用预览 capability 需当前状态复核；直达对象 URL 最长持续至其有限 TTL |
| 归档素材          | 正常团队与公开入口不再授权；管理归档入口按权限可见             | 既有直达 URL 同样存在 TTL 窗口；已获得的字节无法收回                  |
| 关闭实例公开      | 所有公开查询/文件资格立即拒绝，包含已登录用户访问公开路由      | 公开 epoch 使旧应用 capability 失效；直达对象 URL 仍受原 TTL 限制     |
| 禁用账号/撤销会话 | 新团队 API/下载/内部预览授权拒绝；既有公开内容不自动撤回       | 直达私有对象 URL 的残余有效期及已开始的传输不能承诺瞬时终止           |
| 角色降权          | 新动作和写入提交使用新角色；失去 publishOwn 后不能更新公开快照 | 曾被合法读取的字节无法收回；尚未提交的有副作用动作须重新授权          |

所有时间界限使用服务端时间。签名 URL、预览 capability、上传授权均必须有最大 TTL，不能由浏览器指定无限时长。具体生产 TTL 数值尚待确认；测试以配置的 `downloadUrlTtl`、`previewCapabilityTtl`、`uploadGrantTtl` 为边界，不能把示例值当作用户承诺。

已开始的流式下载可以结束，后续 Range 请求必须重新通过当前有效 URL/资格判定；若业务将来要求撤回时强制中断所有连接，需要独立网关方案及成本评估，不属于现有有限 TTL 承诺。

### 7.3 缓存与公开开关

- 首期团队 API、公开资格检查、签名 URL 响应使用禁止共享缓存的策略；公开元数据首期也采用 `no-store`，先保证撤回正确，不提前引入可绕过状态判断的 CDN HTML/JSON 缓存。
- 原始字节和派生物可按不可变内容缓存，但每次交付仍须满足当前授权合同；不能把私有对象 URL 转为永久公共路径。浏览器/代理已收到的内容不属于可远程擦除范围。
- 搜索索引和异步投影不作为公开资格真相。返回前对 active、归档、公开开关及目标版本进行当前校验；旧事件带 revision，不能让已撤回内容重新出现。公开计数和分面不能从团队索引直接取值。
- 公开开关关闭时递增 `publicAccessEpoch`，撤销旧的应用级公开能力；不修改素材所有权，不删除文件，不悄悄改写 Publication 为已撤回。
- 重新开启公开采用已确认决策 **D01**：当前仍 active 且版本/素材仍有效的公开快照恢复可见；管理界面在显式开启操作前说明影响数量和语义。epoch 只使旧应用 grant/capability 失效，不阻止对这些有效快照签发新 grant；不要求 owner 因总开关曾关闭而逐项重新公开。该重开语义已获明确确认；这不意味着授权/缓存实现或相关验收已经完成。
- 服务重启、角色缓存、浏览器返回缓存、后台预览页面和 Service Worker 都不能恢复已撤销资格；首期不缓存私有签名响应到可持久共享缓存。

## 8. 并发控制、拒绝语义与审计

### 8.1 前置条件与错误合同

| 场景                                             | 约定                                                                                           |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 缺失/无效/撤销的会话访问团队入口                 | `401`，稳定身份错误码；不回显账号存在性                                                        |
| 资源本身不可见，例如他人上传工作区               | `404`，不泄露所有者、状态或对象存在性                                                          |
| 资源可见但动作无权，例如普通成员编辑他人团队素材 | `403`，稳定权限错误码                                                                          |
| 有效会话需要再次确认密码                         | `403 FRESH_AUTH_REQUIRED`；原业务操作尚未执行；确认不提升能力，随后仍校验权限、状态与 revision |
| PATCH 缺必需 `If-Match`                          | `428 PRECONDITION_REQUIRED`                                                                    |
| PATCH 的 `If-Match` 过时                         | `412 PRECONDITION_FAILED`，不得覆盖新内容                                                      |
| 动作 POST 缺必需 `expectedRevision`              | `428 PRECONDITION_REQUIRED`                                                                    |
| 动作 POST 的 revision 过时或资源状态已变化       | `409`，区分 revision 冲突与状态冲突的稳定 code                                                 |
| 上传 cancel/retry                                | 不要求 expectedRevision；使用当前状态、任务 fence 与幂等键，不因缺 revision 返回 428           |
| ready 后请求取消上传                             | `409 UPLOAD_ALREADY_READY`，提示转为归档；不删除素材                                           |
| 公开已撤回、归档或实例公开关闭                   | 公开资源入口统一不可用响应，不泄露内部状态；全站关闭可用公开配置表达关闭页面                   |
| 未知 permission、非法配置或不支持的输入格式      | `422` 或相应用例明确的输入错误；不能静默忽略后继续                                             |

身份/可见性检查先于返回冲突细节，避免用 revision、状态码枚举他人的私有资源。具体 code 与 API 文档共同冻结，表中状态优先于 UI 猜测。

### 8.2 事务与迟到结果

角色/账号/设置变更和资源写入需要可说明的串行化点。建议短事务内以一致顺序校验当前 actor、角色/授权 revision、必要实例策略和资源行，再执行状态更新；所有路径遵守同一锁顺序。慢对象 I/O、视频处理、动效运行放在事务外；回来后重新检查，不沿用动作开始时的鉴权快照。

归档与公开、撤回与更新公开快照、取消与 worker ready 提交使用条件更新/行锁和 revision 栅栏：

- 若 ready 提交先成功，取消返回状态冲突，用户可归档；若取消先提交，worker 迟到结果不能入库。
- 若归档先成功，公开必须拒绝；若公开先成功，随后的归档必须在同一事务撤回它。
- 若撤回先成功，旧 revision 的公开更新不能复活；再次公开须 owner 明确执行新的公开动作。
- 权限变化先提交后，尚未提交的旧请求不得再完成受限副作用；若业务副作用先合法提交，随后降权不会篡改已经发生的审计历史。
- 幂等键约束重复命令，不替代授权；重试请求仍检查当前 actor 与权限。已经完成的原操作可返回有限的幂等结果，不能借此重新签发已失效的文件权限。

关键写入与审计在同一业务事务提交：公开/撤回、归档/恢复、权限角色变更、账号停用、标签字典维护、配置变更、治理性取消/重试。审计记录 actor、动作、目标、结果、requestId 和必要 revision，不记录密码、恢复令牌、签名 URL、云密钥或整个请求体。操作日志和审计分开；数据库运维权限不属于产品角色承诺范围。
